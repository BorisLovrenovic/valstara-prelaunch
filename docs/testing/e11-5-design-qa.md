**Finding A1 — the sticky bar could not be reached by keyboard. Fixed (founder decision 2026-11-13).** The bar (`[data-dock]` in `src/islands/SignupForm.astro`) follows the hero form in the document and shows only while the hero form is off screen. Tabbing forward past the hero brings the bar in, but focus is already below it. One Shift+Tab steps back to the catalogue and then into the hero, which scrolls the hero back into view and hides the bar again, so its field and Join button are never focused. The probe recorded this order, backward from below the hero at 390px: catalogue track, catalogue track (`bar=true`), catalogue track (`bar=false`), marketing checkbox, hero Join, hero email. The same signup is fully keyboard-operable through the header's Join link and the hero form, so this is not a loss of function under WCAG 2.1.1, but a keyboard user can never use the bar a pointer user sees. The founder chose to make the bar reachable (plan, E11.5-12 founder decision 1). The island now has a keyboard stop right after the bar, fixed where the bar opens so focusing it never scrolls the page. Reaching it opens the bar and moves focus inside, to the field going forward (Tab from the hero form's last control) and to Join going backward (Shift+Tab from the first control after the hero). While focus is inside, the bar stays open even with the hero in view, and the stop leaves the tab order, so Tab and Shift+Tab move on past the bar. Focus landing anywhere else hands the bar back to its usual rules. The stop is never shown at 48rem and up, without JavaScript, or after a hero signup. The bar has no form of its own, as built, so Join submits it, and Enter in its field does not. `test/accessibility.test.mjs` drives that path: Tab into the bar's field, Tab to Join, Tab past the bar, Shift+Tab back to Join and the field, Join with the field empty (the error is announced and linked), then a real signup to the bar's confirmation and Close. "The sticky bar is never a tab stop at 48rem and up, or without JavaScript" covers 768 and 1440px and no JavaScript. With the stop removed, the first assertion fails.

**The spoken pass on the final design, 2026-11-13.** The same method as E11-03: Orca 46.1 with Speech Dispatcher and eSpeak NG, against headed Playwright Chromium 1.62.1 (`--force-renderer-accessibility`) in Xvfb, in a scratch container built from the pinned Playwright image with those packages added. The repository gained no dependency. The app ran from this branch's build against a disposable migrated database. Playwright's keyboard drove the page, with Turnstile's callback simulated and the signup responses answered in the browser, so no mail was sent and no subscriber was stored. Orca's `--debug-file` recorded, per action:

The speech was captured from a PulseAudio null sink's monitor, 64 s of 44.1 kHz two-channel PCM: −15.9 dB mean and 0.0 dB peak, so synthesis produced audio and not only log lines. The request form's empty-submit path was not exercised, because its button stays disabled until Turnstile's implicit widget answers, which the stand-in does not render; that form is native HTML (`required`, `type=email`), unchanged in behaviour by E11.5. The first run could not speak the mobile sticky bar, because focus never reached it (finding A1). The bar's run, after A1's fix, captured 31 s of speech at −16.2 dB mean.

**Finding S1 — the bar's confirmation was not spoken. Fixed.** After a bar signup, focus moves to Close, as E11.5-11h specifies. Orca received the polite status "Check your inbox." but the focus change interrupted it, so a screen-reader user heard only "Close push button." and not that the signup worked. Close now carries the confirmation line as its description (`aria-describedby`), so it is read with the button. Copy, focus and the visible row are unchanged. The sticky-bar journey in `test/accessibility.test.mjs` requires Close's description to be the confirmation copy.

**Finding L1 — the open security check overflowed the hero at 320px. Fixed.** The contact sheet's state `signup-08-security-check-visible` failed the layout checks at 320px in both themes: horizontal overflow, with the form, its section and `main` overflowing. Cloudflare's normal widget is a fixed 300px wide, the size `Hero.dc.html` draws, and the card's content box at 320px is narrower. The canvas has no 320px frame. `SignupForm` now asks Turnstile for its compact widget (150 × 140, the size the task pages already use) when the form's content box is narrower than 300px, and the normal widget otherwise. That is 320 and 360px; 390px and up keep the drawn widget. `test/landing-hero-rendered.test.mjs`, "the open Turnstile widget fits the form card at every design width", opens the widget at every design width and requires the size, the widget inside the form, no horizontal overflow and a clean layout check. It fails at 320px when the island always asks for the normal widget. The behaviour is unchanged: the same widget, token and callbacks.

**Finding E1 — email links were smaller than the 44px tap target. Fixed (founder decision 2026-11-13).** The contact sheet applies every layout rule to the email previews except the container grid. At 320, 360 and 390px every template's text links fall short of 44px: the footer's "Unsubscribe from Valstara email" (187 × 15) and each secondary link (116–170 × 17, or about 41px tall where a long label wraps, as in the winner email's rules link). The primary button is 44px, as E11.5-11 requires. E11.5-11 specified "secondary links as text" and required only buttons to be 44px tall, and design rule 8's enforced set is rendered pages, so the email layout does not break a rule it was built to. The site, though, makes every standalone link a 44px target below 48rem. The founder chose 44px links (plan, E11.5-12 founder decision 2). `template-layout.ts` gives each secondary link's cell the class `v-link` and the unsubscribe line `v-link-small`. The head's style block makes their links blocks padded around their one line, (44 − 24) / 2 = 10px for body links and (44 − 20) / 2 = 12px for the footer's, from `--tap-min` and the leading tokens, at every width. The anchors stay plain `<a href>` text links, so the E8-03 and E11.5-11 suites, which pin that markup, pass unchanged. A client that drops the head's `<style>` block shows the links as before. `test/email-layout.test.ts`, "E11.5-12 every link in every template is at least 44px tall", requires both rules at 44px or more and every link in every template to be the button or in a tap-link cell. It fails when either padding is halved.
