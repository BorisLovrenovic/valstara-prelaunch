# Feature: Signup

## Summary
One form, one required field. The visitor gives an email address, passes an invisible challenge, and can make separate optional choices about marketing and, under the 13+ policy, the 18+ giveaway. **No country or location is asked** (ADR-026). **The form is one of only three interactive islands on the site** (ADR-001).

## Feature flag
`signup.enabled` — default on. Off renders an honest paused message in place of the form, never a form that fails on submit.

`waitlist.age_13` defaults off. The enable command refuses until `reviewedWordingInPlace` is true. E11.8-07 applies the P12 review, publishes the rules revision and sets the prerequisite. Until then production keeps the 18+ statement and the existing signup form.

## User flows
1. **Land** — from social, search, or a referral link carrying `?ref=CODE`. The referral code is read **server-side during the rendering request** and returned as a signed, expiring hidden field (ADR-008).
2. **Marketing opt-in** — the optional box starts unticked. The 13+ form uses draft wording `v2`, which affirms the visitor is 16 or older. The 18+ form uses `v1`. Retained rendered wording versions remain accepted within the same age policy. A valid tick records the submitted version as pending consent until verification. Marketing never affects joining or giveaway entry (ADR-027).
3. **Age and giveaway** — every signup placement shows the joining age beside the submit button, 18+ with the flag off and 13+ with it on. The 13+ form offers a separate, unticked box affirming 18+ and asking to enter the giveaway. Neither box is required to join. The mobile bar submits the hero form's choices. A member who still needs the giveaway box can use `/me` while the flag is on and entries are open. Provisional winners confirm their age at award time.
4. **Submit** — the server verifies Turnstile and applies the IP-prefix rate limit, then compares the age policy issued with the rendered form with the current policy. A mismatch in either direction asks the visitor to load the current form and submit again, before any signup effects and regardless of the address's membership status (D-083).
5. **Response** — "any next step will arrive by email". The same accepted response covers a new, pending or verified address. **No position, no count, no rank and no membership signal.**

E11.5-06 presents that identical accepted response as a client-side check-your-inbox panel. It echoes only the address the visitor typed, conditionally describes the verification email, and offers a different-address control. After 60 seconds it offers resend through the existing `/api/resend-verification` route with a fresh Turnstile token. The route's acknowledgement is identical for unknown, pending and verified addresses. E11.5-11g styles every form state from the wireframes (`docs/brand/page-design.md`): field errors under the field, form-level messages as a focused notice above the label, a spinner in the disabled button while the security check or the request is in flight, the success and paused panels, and the neutral notice when JavaScript is disabled. The flow and its copy are unchanged. E11.5-11m restyles those states and the bar to the final design and adds state motion: the form fades out before the success panel enters, "Use a different address" reverses it, notices, field errors, the resend control and the in-flight label fade in, and the bar slides in over 200ms. Every transition is CSS, lasts at most `--duration-base`, and does not run under `prefers-reduced-motion`. Focus targets, the 60-second resend delay (counted from the panel appearing), the copy and the submission contract are unchanged. One behaviour changes (founder decision 2026-11-07): a form-level notice describes the last attempt only, so every new submission clears it, as it already cleared the field and bar errors.

At small widths (below 48rem), the same island has a server-hidden bottom signup bar that slides in once the hero form leaves view. It hides while the hero form or the footer is visible. The bar mirrors its email value with the hero input; only the hero input is named `email`, and the bar submits the existing form, including the untouched signed referral field and the optional hero marketing checkbox. A successful bar submission collapses to a closable one-row confirmation (`role="status"`), which follows the same hero and footer rules until it is closed. If the bar closes or hides with focus inside it, focus moves to the hero confirmation without scrolling. The bar has no separate challenge widget, form, script, storage or marketing checkbox. While it is visible, the page reserves its measured height as bottom padding and sets the scroll padding to that height plus 16px, so a focused element lands at least 16px clear of it. Only the element that received focus is lifted, and only while it still holds it, so a bar submission whose Join is disabled in flight (focus drops to the page) is never scrolled to the footer and closed; the bar stays open and shows its own confirmation. Its bottom padding respects `env(safe-area-inset-bottom)`. Without JavaScript or with `signup.enabled` off, it remains absent. The bar's layout is in `docs/brand/page-design.md` (E11.5-11h).

E11.7-08 adds the collapsed “Have a referral code?” disclosure after the marketing checkbox in the landing hero, controlled by `referral.enabled`. The browser's native keyboard and pointer controls open it. An untouched prefill follows the signed-link path. A replacement is looked up case-insensitively as a typed code, and clearing the field removes attribution. An unknown or inactive replacement still reaches the check-your-inbox panel, with “This referral code could not be applied.” The note depends on the submitted code and is the same for new, pending and verified addresses. Without JavaScript the native POST carries the typed field and receives HTTP 400 `challenge_failed` because it lacks the Turnstile token (D-062). The mobile bar still submits the hero's whole form, including any referral fields. With referrals off the ordinary signup stays available.

## The waitlist at 13 and over (E11.8-06)

New subscriber records keep the age policy under which they were created, including records created through 18+ partner and student ambassador applications. The first signup giveaway tick can be recorded when creating the subscriber or on a repeat signup while the record is pending. It is evaluated at verification. After rollback, a fresh 18+ form for an existing pending 13+ record receives the ordinary signup response and leaves pending marketing consent unchanged. Any valid 16+ opt-in already on that record is promoted normally at verification (D-084). The [giveaway eligibility rules](giveaway.md#entry-after-the-age-policy-change) apply to both live accrual and reconciliation across flag changes.

## Edge cases and error states
Address already `pending` → the verification mail re-sends, subject to its own rate limit, and the response is identical. Address already `verified` → the same accepted response and no second verification mail. The page never offers a status link based on that result; membership is disclosed only to the address owner. Turnstile fails or expires → an honest retry prompt and no request is sent without a valid token. Turnstile provider times out → strict rate limiting and a review flag rather than an open door. Rate limit hit → an honest wait time, never a silent no-op that looks like success. JavaScript disabled → the page and form render with an explicit enable-JavaScript notice; a native submission is rejected because Turnstile has no no-JS token path. Blocklist/MX decisions belong to E5, referral attribution to E4, fraud decisions to E5, and giveaway entry to E7.

## Acceptance criteria
- [ ] Signup completes with **email only** — no country, region or other location field exists (ADR-026)
- [ ] Turnstile is verified **server-side** before any other work — asserted by test
- [ ] The email is **normalised before the uniqueness check**, and both the raw and normalised forms are stored
- [ ] `?ref=` is read on the server and returned signed; **no cookie and no client-side storage is involved** — asserted by test
- [ ] The marketing opt-in renders **unticked**, and a ticked or unticked submission gets the identical response and the identical waitlist and giveaway treatment (ADR-027)
- [ ] The active joining-age statement renders next to the submit button in every placement, from the copy layer. With `waitlist.age_13` on, both boxes start unticked, operate independently and are optional
- [ ] A stale age-policy form gets the same fresh-form response for any address, with no signup effects. A fresh 18+ form on rollback preserves pending marketing consent for an existing 13+ record
- [ ] A double submission produces **one** subscriber, **one** referral edge and **one** verification email
- [ ] Unknown, pending and verified addresses receive the **identical accepted response**; membership is never disclosed by the page
- [ ] The response body contains **no position, count or rank**
- [ ] With JavaScript disabled the form renders an enable-JavaScript notice and its missing/empty Turnstile token is rejected by the real route
- [ ] Every error path renders copy from the copy layer, in brand voice

## Telemetry
Form view, submit attempt, submit success by source, marketing opt-in rate, rejection reason mix, Turnstile failure rate, ref-carrying share of signups.
